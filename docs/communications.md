# Заявки, переписка и поддержка Event Match

Реализовано 23 сентября 2026 поверх аккаунтов Firebase Auth/Firestore. Заявки связаны с реальными опубликованными профилями и сохранёнными мероприятиями. Проверка выполнена локально с Firebase Emulator; облачное развёртывание остаётся отдельным шагом. Биллинг, Functions и Storage для коммуникаций не требуются и не включались.

## Как пользоваться

- В живом каталоге кнопка «Обсудить мероприятие» открывает заявку выбранному подрядчику. Для гостя адресат сохраняется при переходе через вход и подтверждение email.
- В кабинетах есть «Заявки и сообщения» и «Поддержка». Клиент выбирает своё мероприятие, реального подрядчика, услугу и вводит первое сообщение. Перед отправкой видит получателя и передаваемые условия.
- В заявке сохраняется снимок названия, города, даты, формата и пожеланий. Изменение мероприятия не меняет отправленную заявку. Адресат — PublishedProfile.ownerId, совпадающий с Firebase UID; 66 анонимизированных анкет не могут получать сообщения.
- Подрядчик принимает заявку к обсуждению или отклоняет её, клиент может отменить. После начала обсуждения любой участник может закрыть заявку. История сохраняется, новые сообщения не отправляются. Начало обсуждения не бронирует дату, не фиксирует цену и не меняет календарь.
- Переписка обновляется через Firestore, история загружается порциями. Непрочитанные обозначены текстом; прочтение записывается только после появления доставленного сообщения в видимой области.
- Отправка ожидает подтверждения сервера. При ошибке текст и идентификатор сохраняются для безопасного повтора. Начать другое сообщение после неопределённого результата можно отдельным явным действием: это новый идентификатор, предыдущее сообщение могло уже дойти.

## Поддержка и приватность

Самостоятельное обращение создаётся в разделе поддержки. Обращение по заявке требует явного согласия передать её переписку. Администратор видит очередь обращений; чтобы отвечать и открывать контекст, он берёт обращение в работу. Модератор карточек этих полномочий не имеет. Администратор не может принять собственное обращение.

Заявка доступна только участникам. Дополнительный доступ получает лишь назначенный администратор связанного обращения в статусе «В работе». Он читает контекст, но не отправляет сообщения от имени участников. Закрытие обращения или отзыв роли прекращает этот доступ.

На заявку действует **одно текущее разрешение поддержки**. Новое связанное обращение передаёт контекст новому обращению и прекращает доступ через прежнее; об этом сказано в согласии перед отправкой. Старое обращение сохраняет свою переписку с поддержкой, но больше не открывает заявку.

Создание, назначение и закрытие обращения попадают в неизменяемый журнал атомарно с действием. Журнал виден заявителю и администраторам. Глобального административного доступа к личным заявкам нет.

## Данные и правила

| Путь | Назначение |
| --- | --- |
| conversations/{id}, kind=inquiry | Участники, снимок мероприятия, услуга, статус, ревизия, последнее сообщение |
| conversations/{id}, kind=support | Заявитель, тема, назначенный администратор, ссылка на заявку, статус |
| conversations/{id}/messages/{messageId} | Неизменяемые автор, текст, серверное время и последовательный номер |
| conversations/{id}/readStates/{uid} | Собственная отметка последнего прочитанного номера |
| communicationAudit/{id}_{revision} | Автор, действие и серверное время создания, назначения или закрытия обращения |

Первая запись и каждое сообщение создаются атомарно с заголовком диалога. Rules запрещают подмену автора, состава участников, исходного контекста, пропуск номера сообщения, выдуманные итоги и действия без аудита. Индексы обеспечивают сортировку личных входящих и очереди поддержки по времени обновления.

Статусы заявки: sent → discussing → closed; sent/discussing → declined подрядчиком, sent/discussing → cancelled клиентом. Поддержка: open → in_progress → resolved; заявитель также может закрыть непринятое обращение. Закрытые диалоги не открываются повторно.

Проверяется текущая подтверждённая сессия, состояние аккаунта и роль. Заблокированный пользователь не читает приватные данные и не пишет; отправка по заявке требует активных обоих участников. Выход, смена аккаунта и роли пересоздают приватный интерфейс и подписки.

Отключение дискового кеша не очищает память Firestore при смене пользователя. Поэтому репозиторий дополнительно не передаёт UI данные из кеша и неподтверждённые записи: каждая подписка ждёт свежий серверный ответ. Если первое подтверждение не приходит за 20 секунд, показывается ошибка с повтором; обычное ожидание новых сообщений не ограничено таймером.

Служебное полное удаление аккаунта очищает его диалоги, связанные обращения, сообщения, прочтения и аудит. Незавершённая очистка безопасно продолжается: временные идентификаторы хранятся в закрытом маркере удаления. Удаление назначенного администратора также прекращает связанный доступ.

## Подключение

Модуль находится в apps/event_match/lib/features/communication/ и разделён на domain, data и presentation. В EventMatchApp репозиторий передаётся через необязательный параметр communications; production создаёт FirestoreCommunicationRepository.

Маршруты: /client/messages, /contractor/messages, /client/support, /contractor/support и /admin/support. Параметр conversation открывает диалог; contractor и event выбирают получателя и мероприятие. Параметры URL не предоставляют прав доступа.

## Проверки и воспроизведение

Flutter-тесты покрывают реальные идентификаторы формы, статусы, повторы после ошибки, согласие на поддержку, непрочитанные, очистку состояния, возврат после входа, пустой URL, повторяющиеся категории, ширины 375/768/1024/1440 и текст 2×. Превью включаются через --dart-define=COMMUNICATION_VISUAL_PREVIEW=true.

backend/test/communication.test.mjs проверяет прямые SDK-запросы в обход UI: приватность, подмену участников/автора/аудита, блокировки, отзыв роли, доступ поддержки и повторяемое удаление. Полный серверный набор на момент интеграции прошёл 56 проверок; отдельный финальный набор коммуникаций — 18.

communication_emulator_test.dart выполняет настоящий Dart/FlutterFire сценарий в Chrome: клиент → подрядчик → поддержка → администратор, повторы отправки, снимок события и серверная изоляция. Отдельно воспроизведён и устранён показ кеша после закрытия поддержки и смены пользователя в том же FirebaseApp/Firestore; обе регрессии прошли. Тест по умолчанию пропущен, поскольку ему нужны изолированные эмуляторы.

Из корня, первый терминал:

```sh
backend/node_modules/.bin/firebase emulators:start --config firebase.communication.json --project demo-communication-smoke --only auth,firestore
```

Второй терминал:

```sh
FIREBASE_AUTH_EMULATOR_HOST=127.0.0.1:9299 FIRESTORE_EMULATOR_HOST=127.0.0.1:8280 node backend/scripts/seed-communication-smoke.mjs
cd apps/event_match
flutter test --platform chrome test/communication_emulator_test.dart --dart-define=COMMUNICATION_EMULATOR_TEST=true
```

Фикстуры допускают только demo-communication-smoke и localhost-порты 9299/8280. Скрипт отклоняет другие адреса и не использует облачные аккаунты. Обычный набор Rules запускается через npm --prefix backend test.

## Границы выпуска

Переписка текстовая, признаки новых сообщений — внутри приложения. Вложения, SMS/email/push, платежи и бронирование в этот этап не входят. Для реальных пользователей нужно завершить [настройку Firebase](firebase.md), опубликовать Rules/индексы и повторить сценарий на рабочем проекте. Android-сборка зависит от установки SDK; проверки Web не заменяют Android.
