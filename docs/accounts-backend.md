# Аккаунты и доступ Event Match

Рабочие кабинеты используют Firebase Authentication и Cloud Firestore. Для них достаточно тарифа Spark: загрузки файлов, Cloud Functions и обращения к LLM не требуются. Firebase-конфигурация проекта `hackalem-84547` уже находится в Flutter-приложении; это публичная конфигурация, а не служебные полномочия.

## Локальная проверка

Нужны Node.js 22/24, Java 21+ и Flutter. Из корня проекта:

```sh
cd backend
npm ci
npm test
```

Тестовый запуск поднимает только Auth (9099) и Firestore (8080) на локальном интерфейсе с проектом `demo-event-match`, загружает действующие правила и удаляет тестовые документы между сценариями. На первом запуске Firebase CLI скачивает JVM-эмулятор. Реальный Firebase-проект в тестах не используется.

Для постоянного локального backend: `cd backend && npm run emulators`. Flutter должен подключать оба эмулятора с тем же project ID; на Android Emulator адрес компьютера — `10.0.2.2`, в браузере — `127.0.0.1`. HTTP-подключение эмуляторов предназначено только для разработки. Дисковое сохранение приватных документов во Flutter отключено.

В другом терминале из корня:

```sh
cd apps/event_match
flutter run -d chrome --dart-define=USE_FIREBASE_EMULATORS=true --dart-define=FIREBASE_EMULATOR_PROJECT_ID=demo-event-match --dart-define=FIREBASE_EMULATOR_HOST=127.0.0.1
```

После регистрации и подтверждения email через Auth Emulator локальному пользователю можно назначить администратора:

```sh
cd backend
FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 FIREBASE_AUTH_EMULATOR_HOST=127.0.0.1:9099 npm run admin -- grant-admin --project demo-event-match --uid FIREBASE_UID --reason 'Локальный администратор' --execute --confirm-project demo-event-match
```

## Хранение и права

| Путь | Содержание | Доступ клиента |
|---|---|---|
| `accounts/{uid}` | Имя, email входа, состояние и ревизия | Владелец читает свой статус даже после блокировки; администратор читает список |
| `accounts/{uid}/events/*` | Личные мероприятия, даты `YYYY-MM-DD` | Только подтверждённый активный владелец |
| `accounts/{uid}/selections/*` | Исторические снимки до трёх рекомендаций | Только подтверждённый активный владелец |
| `accounts/{uid}/favorites/*` | Явно сохранённые живые карточки | Только подтверждённый активный владелец |
| `accounts/{uid}/eventPlans/{eventId}` | Выбор команды, общий бюджет, checklist, заметки и ревизия | Только подтверждённый активный владелец; запись требует существующего события |
| `staffAccess/{uid}` | `admin`, `moderator` или `none`, ревизия | Владелец читает свою роль; администратор назначает/снимает модераторов с аудитом |
| `profiles/{uid}` | Приватная версия профиля, статус и замечания | Владелец и сотрудники; отправленная версия заморожена |
| `publishedProfiles/{uid}` | Проверенный снимок карточки | Гости читают только `published == true`; запрос списка обязан содержать этот фильтр |
| `calendars/{uid}/months/YYYY-MM` | Занятые дни и серверное время подтверждения | Владелец меняет; опубликованные календари доступны гостям, остальные — владельцу и сотрудникам |
| `audit/{type}_{uid}_{revision}` | Автор, действие, причина, серверное время | Сотрудники читают; создание только вместе с соответствующим действием; изменение/удаление запрещено |
| `deletedAccounts/{uid}` | Минимальный служебный маркер удаления | Любой клиентский доступ запрещён |

Отсутствие роли означает обычный аккаунт. Роль администратора нельзя выдать через клиентский SDK, в том числе действующему администратору. Все неизвестные коллекции запрещены; серверные коллекции параллельно разрабатываемого помощника также не открываются этими правилами.

Проверка прав обращается к текущим документам, поэтому блокировка аккаунта и отзыв роли действуют на следующие защищённые операции без ожидания обновления токена. Смена кабинета не меняет полномочия. Email авторизации не копируется в публичный контакт.

## Транзакции и модерация

- Каждая новая запись с ревизией начинается с `1`; последующее изменение увеличивает её ровно на один. Изменение имени, черновика и календаря не требует записи аудита.
- Владелец может сохранить черновик, отправить полную карточку или отозвать отправку. Отзыв сохраняет содержимое; редактировать его можно следующим действием.
- Решение по проверке меняет только статус, причину, ревизию и время. При одобрении та же транзакция записывает публичный снимок именно проверенной версии и создаёт `audit/profile_UID_REVISION`.
- Сотрудник, у которого есть собственный профиль подрядчика, не может проверить свою карточку: её должен рассмотреть другой модератор или администратор.
- Правила проверяют новую, ранее отсутствовавшую запись аудита через `getAfter()`, её автора, ревизию, действие и `request.time`. Старую запись невозможно повторно использовать для новой публикации.
- Снятие карточки с публикации увеличивает её отдельную ревизию и создаёт аудит `publication`. Публичный снимок и календарь хранятся отдельно: проверка карточки не стирает свежие занятые даты.
- `suspended` и `deactivated` требуют в той же транзакции скрыть текущую публикацию и записать оба аудита. Восстановление из `suspended` не публикует карточку автоматически. Деактивация не отменяется клиентом.
- Клиентские действия не могут блокировать или деактивировать администраторов. Перед деактивацией администратор передаёт полномочия другому человеку и снимает свою роль доверенным инструментом.
- `deletionRequested` выставляется только при деактивации владельцем. Полное удаление выполняет служебный инструмент, описанный ниже.

Календарь принимает только реальные дни указанного месяца, без повторов, и серверное время подтверждения. Политика подбора проверяет свежесть подтверждения (30 дней); правила не выдают обещаний о бронировании.

## Доверенное обслуживание

Команды используют Application Default Credentials оператора с правами Firestore и Firebase Authentication. Не добавляйте ключ service account в репозиторий, Flutter assets или `--dart-define`. Эмуляторный запуск допускается только при одновременно заданных `FIRESTORE_EMULATOR_HOST` и `FIREBASE_AUTH_EMULATOR_HOST` и проекте с префиксом `demo-`.

По умолчанию инструмент выполняет только чтение и показывает конкретное предстоящее изменение. Для выполнения необходимы `--execute --confirm-project PROJECT`.

Первый администратор сначала регистрируется обычным способом и подтверждает email. Пример просмотра:

```sh
cd backend
npm run admin -- grant-admin --project hackalem-84547 --uid FIREBASE_UID --reason 'Первый администратор Event Match'
```

Выполнение после проверки UID:

```sh
npm run admin -- grant-admin --project hackalem-84547 --uid FIREBASE_UID --reason 'Первый администратор Event Match' --execute --confirm-project hackalem-84547
```

Инструмент проверяет активный аккаунт, подтверждение email и отсутствие блокировки Auth. Назначение администратора создаёт запись служебного аудита. Никаких паролей и фиктивных аккаунтов подрядчиков команда не создаёт.

Снять роль администратора можно командой `revoke-admin` с теми же аргументами. Она требует, чтобы оставался другой активный администратор с подтверждённым и включённым аккаунтом Firebase Auth. По умолчанию это также просмотр; исполнение требует `--execute --confirm-project PROJECT`. Проверка роли и обновление выполняются транзакционно, поэтому два параллельных отзыва не могут оставить систему без администратора. После снятия роли владелец может запросить обычную деактивацию или удаление через настройки.

Для удаления пользователь должен выбрать запрос полного удаления в настройках. Просмотр:

```sh
npm run admin -- delete-account --project hackalem-84547 --uid FIREBASE_UID --reason 'Подтверждённый запрос владельца'
```

С теми же `--execute --confirm-project hackalem-84547` команда сначала устанавливает служебный маркер, отключает пользователя Auth и отзывает refresh-токены, затем удаляет личные коллекции, профиль, календарь и роль. Скопированные карточки удалённого подрядчика удаляются из чужого избранного и исторических подборок; остальные записи сохраняются. Аудиты об удаляемом объекте удаляются, а авторство его прежних действий над другими объектами обезличивается. Firebase Auth удаляется последним. Повторный запуск после сбоя безопасно продолжает очистку.

Минимальный `deletedAccounts/{uid}` сохраняется без email, имени и контактов, чтобы ещё действующий старый ID-токен не мог воссоздать аккаунт. Правила также запрещают повторное сохранение снимка удалённого подрядчика. Служебные команды обходят Rules по назначению, поэтому их полномочия нельзя передавать пользовательскому приложению.

## Подключение реального проекта

1. В Firebase Console включить Authentication → Email/Password и Google, настроить support email и разрешённые домены Web. Для Android зарегистрировать SHA-1/SHA-256 сертификатов разработки и релиза в Firebase, затем получить актуальную конфигурацию Google Sign-In.
2. Создать Firestore в Native mode и выбрать регион до загрузки пользовательских данных. Убедиться, что проект остаётся на Spark. Не включать биллинг для кабинетов.
3. Из корня проверить `backend/node_modules/.bin/firebase deploy --only firestore:rules,firestore:indexes --project hackalem-84547`. Команда публикует только правила и индексы, не Functions и не Storage. Выполнять после локальных тестов и проверки целевого проекта.
4. Зарегистрировать реальные проверочные аккаунты клиента и подрядчика, назначить первого администратора доверенным инструментом. Проверить цепочку «отправка → проверка → календарь → живая рекомендация → сохранение» в Web и Android.

Само наличие этих файлов не означает, что провайдеры включены или Rules уже опубликованы в реальном проекте. Пустой живой каталог не заменяется демоданными; исходные 66 анкет остаются отдельным локальным демонстрационным набором.

## Проверяемые сценарии

`backend/test/firestore.test.mjs` проверяет доступ напрямую через SDK: приватность даже от администраторов, email verification, запрет повышения роли, заморозку отправленного профиля, согласованность проверенной версии, конкурентные решения, подделку/повторное использование аудита, реальные календарные даты, блокировку и восстановление без публикации, отзыв роли, отсутствие доступа к неизвестным коллекциям, работу служебного bootstrap и повторяемую очистку аккаунта. Это проверки сервера доступа, а не только видимости кнопок интерфейса.
