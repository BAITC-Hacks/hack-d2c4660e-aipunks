# Развитие продукта

## Основа

Форма создаёт типизированный `MatchRequest`: обязательные city/date/format/category/budget, опциональные hours/language/preferences. `validate()` защищает границу домена, `toJson()` фиксирует поля будущего API. Форма остаётся источником подтверждённых условий даже после появления ввода одной фразой.

`MatchingController` управляет загрузкой каталога и состояниями idle/searching/success/failure. Подбор выполняется через `RecommendationService`; `LocalRecommendationService` — рабочая реализация на JSONL и чистом Dart. Интерфейс внедряется через `EventMatchApp(recommendationService: ...)`. Тема вынесена в `app/app_theme.dart`.

Сервис имеет признак `supportsPreferences`. Локальный вариант честно сообщает, что пожелания не учитываются. Поле передаётся в запросе, но не хранится между запусками. Никакой имитации AI или обещания локального смыслового анализа нет.

## Контракт будущего API (проект, сервер ещё не реализован)

`POST /v1/recommendations`, JSON:

```json
{
  "city": "Алматы",
  "date": "2026-11-14",
  "event_format": "свадьба",
  "category": "Ведущий",
  "budget_kzt": 1000000,
  "hours": 5,
  "language": "русский",
  "preferences": "Камерная свадьба без шумных конкурсов"
}
```

Ответ: `outcome` (matched/category_absent/no_eligible), `recommendations` (до 3 объектов contractor + explanation), `summary`, `dataset_version`, `algorithm_version`. Contractor использует поля исходного JSONL. Ошибки валидации — HTTP 422 с ошибками полей; недоступность сервиса — 503. Это контракт для следующей реализации, не существующая конечная точка.

В будущем добавляем `ApiRecommendationService implements RecommendationService` и выбираем его в точке сборки приложения. HTTP-клиент, URL, DTO-преобразования, таймауты и ошибки живут в data, API-ключ LLM — только на сервере. Клиентский таймаут сейчас 10 секунд. После редактирования формы поздний ответ игнорируется; это не отмена сетевого запроса на транспортном уровне.

## Последовательность развития

1. Качество рекомендаций: признаки из описаний, фактические индивидуальные объяснения и проверки на реальных 66 профилях.
2. Backend/AI: реализовать контракт, добавить адаптер клиента, тесты контракта и серверный кэш.
3. Ввод одной фразой: отдельный сервис разбора → черновик формы → подтверждение пользователем. Не выдумывать пропущенную дату или бюджет.
4. Сохранённые подборки и история — отдельные features с собственными репозиториями; после определения пользовательского сценария добавить маршрутизацию и хранение.

Не добавляем заранее пустые кабинеты, оплату и бронирование: они не входят в текущее задание. Новые функции складываем в `lib/features/<feature>/{domain,data,presentation}`, общий UI — в отдельный слой только по мере реального повторного использования.

## Проверка изменений

Из `apps/event_match`: `dart format lib test`, `flutter analyze`, `flutter test`, `flutter build web`. CI запускает те же проверки. Контроллер тестируется подменным сервисом; ядро — без UI; адаптивность — на ширинах 375, 768, 812, 1440 и с увеличенным текстом. Мобильные сборки отдельно проверяются на Android и macOS/iOS.
